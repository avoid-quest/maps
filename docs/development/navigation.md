# Android navigation implementation and acceptance

Version 0.1.8 / Android code 9 introduced explicit navigation; the current interface uses **Avvia** for walking, cycling and driving, and **Segui viaggio** for the selected transit journey (in Mezzi the primary action is **Cerca percorsi** until transit alternatives exist; it never starts road guidance). Route previews and saved itineraries remain planning until that action succeeds. Navigation is Android-only; the browser and Expo Go cannot run the native session.

The local Expo module uses Ferrostar **0.57.0** for road progress, maneuver triggers and route deviation. Android owns platform positioning (GPS, plus the platform fused and network providers when the system offers them), the location foreground service, bounded FOSSGIS requests and offline Italian text-to-speech. This uses the published native core through UniFFI/JNA, with the existing MapLibre renderer and NativeWind interface. No Ferrostar React Native package, Compose UI, Google location service, account, paid routing provider or application backend is required.

## Implemented behavior

While waiting, the interface shows elapsed time and the latest fix accuracy against the required bound; after 30 seconds without a usable fix it settles into a stable "position not found" state with Retry and Stop. Every mode may start from a fix of 50 metres or better after 15 seconds, visibly labelled as a reduced-accuracy start. Guidance continues with fixes up to 50 metres; a fix worse than the mode's normal accuracy shows a reduced-precision label instead of pausing. Three consecutive rejected samples (beyond 50 metres, stale, invalid or implausible jumps) or 8 seconds without an accepted one suspend guidance; one accepted fix resumes it (two distinct fixes when driving). The native module compiles and the JVM policy/transition tests pass. These checks cover deterministic request spacing/cooldown/cancellation, fix/reroute policies, session lifetime, Italian instructions and transit transitions. **Complete physical-device acceptance of Ferrostar/JNA, GPS, TTS and foreground-service lifetime remains outstanding.** Limited development-client route/position observations do not establish outdoor progress, audible voice or screen-off reliability. Browser simulations exercise the interface; they do not close these native gates. The production browser notice viewer was inspected at 320 and 390 pixels: Ferrostar BSD, desugared OpenJDK GPL/exception and UniFFI MPL texts expand with fetch blocked, with zero fetches and no horizontal overflow. This is offline notice/interface evidence only. Final build, signature, bundled JavaScript, notice presence and 16 KB alignment need inspection on the exact release artifact. Keep observed results in [delivery.md](delivery.md), separate from this source contract.

Road guidance consumes one [packaged policy](../../modules/avoid-navigation/android/src/main/assets/road-guidance-policy.json), shared by native fix admission and the core trajectory tests. Fix admission is per mode: walking starts at 35 metres, cycling and driving at 30 metres. Guidance accepts up to 50 metres in every mode, labelling fixes worse than the normal accuracy (35 metres walking, 25 metres cycling and driving). Fixes older than 15 seconds are rejected. All road modes use Ferrostar's entry-and-snapped-exit progression with per-mode distances: passing a turn does not require a sample inside a tiny point checkpoint, lateral offset alone does not complete it, and a short final step does not require travelling beyond the destination. Step advance and arrival evaluate every fix accepted for guidance; deviation is judged only on fixes of 25 metres or better, coarser fixes neither declare nor clear deviation, and rerouting additionally needs three consecutive tight off-route fixes, so a poor signal cannot trigger a reroute. Start payloads are built explicitly (`src/domain/navigation-payload.ts`) from the fields native code reads, with absent optional fields omitted: Expo Modules rejects a nested `undefined` or `null` inside a `Map<String, Any?>` argument with ERR_UNEXPECTED before the Kotlin body runs, and the checkpoint's JSON rejects non-finite numbers. Native snapshots expose current location confidence separately from retained route/admission errors, so a lost fix cannot silently remain a transit replanning origin. Session transitions, commands and fix decisions are logged under the `AvoidNav` tag as fixed codes with bounded metadata (mode, state flags, accuracy, provider, fix age, counters, plan age in minutes and exception class names), without coordinates, destinations, itinerary contents or raw native messages.

The [host trajectory harness](../../tests/navigation-core/README.md) executes the real Ferrostar 0.57.0 Rust controller against that policy. It covers sparse turn samples, sidewalk offset, progress/deviation at accepted accuracy and a short final step. It does not execute the Android library or UniFFI/JNA bridge; Android runtime and physical-route acceptance remain separate.

## First-person guidance presentation

Road guidance uses an app-controlled MapLibre camera fed only by accepted native navigation state: no second location stream and no MapLibre user tracking. The native snapshot exposes, besides the Italian text, structured maneuvers and kinematics (`src/domain/navigation.ts`):

- `upcomingManeuver` (Ferrostar's `remainingSteps[1]`, whose text is `instruction`) and `followingManeuver` (`nextInstruction`) carry the raw OSRM type, modifier, roundabout exit, street name/ref, bearings, driving side, maneuver coordinate and its index in the route geometry. Ids are `<routeRevision>:<step>` and change on every reroute. `followingManeuver` adds the distance/time between the two maneuvers. Raw facts are kept beside Ferrostar's parsed steps because the adapter empties its visual instructions; Italian prose is never parsed back into types.
- `routeProgress.traveledMeters` is the snapped position measured with the native haversine on the bridged route geometry, so the interface can split travelled and remaining route on exactly what it draws. `snappedLocation` and `alignment` (`aligned`, `deviating`, `unknown` when the fix was too coarse to judge deviation) tell the camera whether the snapped position is credible.
- `location` adds speed, course and their accuracies when the platform supplies finite values, plus the monotonic `elapsedMs` sample time used for fix intervals and duplicate detection.

The camera planner (`src/features/navigation/guidance-camera.ts`) produces one frame per distinct fix. The map eases linearly to it over the measured fix interval, so the puck (drawn at the camera anchor while following) and the map move on one clock with React rendering at 1 Hz. It is course-up with circular filtering (the short way across north) and holds its bearing when slow; pitch, zoom and the puck anchor are per mode (walking 34°, zoom 18.3, 67% of the map left between banner and strip; cycling 42°, 17.1–18, 71.5%; driving 48°, 15.7–17.7 by smoothed speed, 73.5%). The anchor is placed with top padding: MapLibre centres the padded rectangle, so bottom padding alone would raise the puck. Turn framing starts 8/10/12 s before the maneuver (walking/cycling/driving), keeps the junction and a short outgoing path (and a second turn that follows within about ten seconds) inside the visible map, and releases over 2–3 s. Cycling and driving draw at the route-snapped position only while `alignment` is `aligned`; walking keeps the real offset. Cycling and driving add a presentation-only lead of at most one fix interval that never passes the upcoming maneuver and stops on degraded, late or recovering fixes; it never feeds navigation state. When a provider omits speed or course, the planner estimates them for presentation only: a displacement counts only beyond the combined horizontal accuracy of the two fixes (at least 3 m, within 10 s), entering motion needs two consecutive consistent estimates, the course accuracy reports the geometric uncertainty, and stationary jitter yields no speed, course or lead.

Camera intent is follow, free or overview. A gesture enters free at gesture start (`onRegionWillChange` with user interaction) and blocks every pending move; **Ricentra** restores the follow pose in one 500 ms transition (in a transit ride or wait it fits the current leg again); overview frames the remaining route north-up and flat once. Fixes and reroutes never take the camera back from free or overview. The visible map is a rectangle: below the banner, above the strip and, in a landscape layout, left of the side panel; anchoring, projection and fits use it. Leaving guidance returns the browsing map to north-up and flat with whichever browse camera command is issued next.

Navigation buildings (`avoid_building_3d` in `src/theme/brand-basemap.ts`) are a hidden native MapLibre `fill-extrusion` layer that guidance makes visible through the same adopted-layer mechanism as the one-way chevrons (`src/features/map/guidance-basemap.ts`). They show in road guidance and transit walks, including free-camera and paused road guidance, but are explicitly hidden in overview, start at zoom 17, fade in over half a zoom level to at most 55% opacity and use one grey per scheme; the tiles' `colour` field is ignored. Height provenance: OpenFreeMap tiles come from Planetiler's OpenMapTiles profile, whose `building` layer carries only `render_height`, `render_min_height`, `colour` and `hide_3d`. `render_height` is `ceil(height ?? building:height ?? building:levels × 3.66 ?? 5)`, so a building without any height or level tag arrives as exactly 5 m, with no field naming the source. The filter drops every feature at 5 m (the default, plus the few real 4–5 m heights, which stay flat), non-numeric or missing fields, tops not above their base and `hide_3d` outlines. No height is ever invented for a missing value. The schema cannot separate measured `height` tags from level-derived approximations (3.66 m per supplied level); both are extruded. The flat footprint layer stays beneath at every zoom. Route visibility comes from layer order: the extrusion sits directly after the flat footprints and before boundaries and labels, the guidance route, casing and junction arrow are inserted before `highway-name-path`, and the map puck, markers and the follow-mode puck image come later still. The pinned MapLibre Native renderer disables depth testing for 2D layers after the first 3D layer (see `PaintParameters::depthModeForSublayer` in Native 13.6.1); this supports placing route layers after the extrusion. Layer-order fixtures alone do not establish actual Android visibility. The order, filter, fade, greyscale and contrast are fixture-tested (`src/theme/map-style.test.ts`, `src/features/map/guidance-basemap.test.ts`). Rendering, occlusion, frame pacing and theme switches with buildings visible need a device or emulator check.

Development builds log `[nav-cam]` rows comparing MapLibre's own `project()` of the camera centre and the next junction with the planner (anchor error, projection error, commanded versus native zoom/bearing). Emulator replays (`adb shell cmd location providers set-test-provider-location` at 1 Hz) exercise this path; physical-device GPS, frame pacing and battery use remain separate acceptance.

## Android acceptance

Build and install following [android.md](android.md). Record version/code, Android version, permissions, installed voice and network state using public routes/stops. Each row above needs an observed result for its affected mode; provider failure is an explicit outcome, and an install alone is not runtime acceptance.

1. Plan without location, then deny and grant approximate/precise location on Start. Pass: planning stays usable; guidance starts only from a valid current precise fix, and manual preview coordinates are never passed off as the device position.
2. Follow a walking route, then separate cycling and driving routes. Check maneuver/voice timing, map following/recentering, remaining estimates, wrong-turn recovery and arrival. Pass: progress matches travel, poor fixes suspend instructions, bounded rerouting recovers or gives an actionable failure, and Stop/arrival end GPS and speech.
3. Follow a transit journey with access walking and a transfer. Compare line/direction/boarding/alighting with operator information, confirm each actual transition, and test an ambiguous loop and absent endpoint. Pass: advisory distance is labelled as straight-line distance; GPS never confirms boarding/alighting; unsupported walking turns and old predictions remain explicit.
4. Repeat screen-off/background, notification denial/Stop, audio interruption, offline/429, UI remount, service/process death and force-stop/relaunch. Pass: stopped work does not return; an interrupted session requires deliberate resume; transit replan is explicit. Measure a sustained physical-device journey and battery use separately from emulator checks.

## Dependency and distribution boundary

The navigation plugin pins Kotlin **2.2.20** / Expo KSP **2.2.20-2.0.3**, D8/R8 **8.13.19**, core-library desugaring **2.1.5** and minimum Android API **25**. The resolved Ferrostar graph also upgrades Kotlin runtime, OkHttp/Okio, coroutines and AndroidX lifecycle components; regression checks must include existing map, HTTP and persistence flows. R8 is a build dependency. The APK runtime graph must still exclude Play services and Firebase.

Navigation code notices are bundled under [the module's third-party assets](../../modules/avoid-navigation/android/src/main/assets/third-party/README.md). Preserve Ferrostar's BSD notice, JNA's publisher notices and applicable JVM/Rust dependency texts and source links when updating the pinned core. Dataset licences and provider usage policies retain their separate terms.
