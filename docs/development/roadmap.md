Audit: 2026-10-11. Released baseline: 0.1.3 / Android code 4; discovery/search changes below are prepared for 0.1.4 / code 5. Reassess the affected rows after implementation changes. Versioned APK and native evidence belong in [delivery.md](delivery.md); installation belongs in [android.md](android.md).

### Transit correctness before daily reliance

The stop board and journey planner are separate sources. GTT board predictions are aged against both feed and entity timestamps. The 0.1.1 correction describes MATO predictions by retrieval time and marks them “Da aggiornare” after two minutes; MATO source timestamps are unavailable, so retrieval time is not proof of live source freshness. An itinerary is not continuously monitored for disruption or a missed connection. No code currently ties a selected MATO leg to a GTT board and replans it.

Selecting Mezzi is the request action; there is no separate MATO consent toggle. Describe this accurately in user documentation. MATO's unresolved reuse/availability policy should remain visible as an experimental-service limitation.

## First Android device session: acceptance evidence

Run these after the installation steps in [android.md](android.md). Record app version, Android version, permission/network state and the exact query or public stop code for each failure. Private home/work coordinates are unnecessary for reports.

1. **Launch and browsing.** With Metro stopped and no Play services in the app's profile, launch, pan/zoom, select a map marker and open/close a sheet using Android back. Pass: real map and local results render, controls remain reachable, and no exit/crash occurs during these transitions.
2. **Discovery and local-only search.** Center within the packaged data bounds; try food/shop categories, plural aliases, a known public venue with a one-letter typo and a street address. Open a food place and a shop. Enable **Solo ricerca locale**, restart and confirm no Photon request during startup or searches; move outside coverage and inspect the outline, radius and capped/empty-result wording. Pass: relevant places retain sources/contact details, saved policy is honored, deliberate missing-data states remain visible and neither uncertain hours nor completeness is invented. A missing name is evidence to investigate, not proof that the business closed.
3. **Permission and origin.** Deny location, plan a walking journey using a chosen map point, then test approximate and precise permission outdoors. During a pending GPS request, choose a manual origin. Pass: the manual choice wins; GPS failure leaves browsing usable; the indicated origin matches the chosen point. The blue point is a captured location, not active tracking.
4. **Road planning.** Use a public destination a few kilometres away and compare walking, bicycle and car. Pass: modes produce plausible paths, distance/duration/steps agree with the map, and the interface never claims navigation has started. Check the arrival entrance and crossings on a familiar walking route.
5. **A real transit journey.** In the rebuilt transit release, plan between two public destinations within the supported network and choose a vehicle result plus a transfer result. Compare alternatives, departure/arrive-by selection, boarding stop, direction, alighting stop and arrival against the operator. Pass: the selected map path and leg details agree, supplied codes/platforms are shown, a cancelled/unknown leg stays explicit and a failed same-query refresh retains the old journey with its age. An all-walking result does not validate vehicles or transfers.
6. **At a stop.** Open the actual public stop code shown on the sign, including the correct side/direction. Compare the next reported departure with the operator. Refresh once, then disconnect for more than two minutes. Pass: no new “live” prediction is fabricated, existing data ages to stale, and unavailable alerts remain distinct from an empty alert list. Empty predictions are allowed; they must not mean “no service”.
7. **Persistence, upgrades and lifecycle.** Save a business, force-stop/relaunch, background during a position request, and switch network connectivity. When a later signed release is available, use the public release or Obtainium update path to install it over the existing app. Pass: favourites persist after both restart and upgrade, the new version is installed without uninstalling, and interrupted requests recover through a useful action. Checking for updates without a newer build does not prove upgrade preservation. Separately note whether an unpersisted itinerary disappears after restart—it currently will.
8. **Comfort and accessibility.** Repeat search/place/route/stop flows with large system text and TalkBack if used. Pass: labels and primary actions remain readable and reachable. Record a 20–30 minute normal-use battery observation as a baseline, not a navigation battery benchmark.

The first session is complete when every step has an observed result, including “unavailable from provider” or a recorded known gap. A successful APK install alone does not close the native runtime gate.

## Data and provider constraints

- **Overture complements OSM; it does not provide Google's business corpus.** Broader downloads can improve coverage without phone accounts or a paid backend, but increase data-preparation/update work. Rich hours/reviews/traffic are separate source problems. See [place discovery](../research/place-discovery.md).
- **Photon is a name/address geocoder, not a complete restaurant-nearby API.** The current category chips deliberately stay local. Better citywide discovery should come from a prepared POI index or a separately evaluated permitted service, not repeated broad public-geocoder calls.
- **FOSSGIS remains modest-use, rate-limited, best-effort routing.** Automatic rerouting must respect its usage policy; a navigation loop cannot simply call it on every location update. See [online services](../research/online-services.md).
- **GTT static and realtime data must stay compatible.** The installed trip lookup can become obsolete even when the feed downloads successfully; refreshing the current package requires developer preparation and a new APK. A scheduled-departure fallback needs additional timetable data and service-calendar handling.
- **MATO's technical accessibility is not a service guarantee or settled reuse contract.** Resolve that dependency before treating transit planning as dependable. An alternative provider should be evaluated against coverage, terms and privacy; accounts or a hosted engine are not automatic prerequisites for the next UI iteration.
