# From the first Android device test to an everyday maps app

Audit: 2026-10-11. Released baseline: 0.1.6 / Android code 7, including local journey/stop persistence, the broader compact place package and reproducible compiler path mapping. Active-view transit refresh is in development; manual acceptance, final review and a new inspected release APK remain pending. Reassess the affected rows after implementation changes. Versioned APK and native evidence belong in [delivery.md](delivery.md); installation belongs in [android.md](android.md).

Version 0.1.2 installed and rendered its bundled main interface with Metro stopped on a Google-free software emulator. An Android system-process ANR blocked healthy interaction checks; the map stayed gray/loading. **Native map/clipboard/location acceptance and physical-device runtime remain unverified.** The main remaining work is retaining useful data during active transit refresh, broadening discovery and place details, and implementing active navigation. Expo/NativeWind remains the selected foundation.

### Transit correctness before daily reliance

The stop board and journey planner are separate sources. GTT board predictions are aged against both feed and entity timestamps. The 0.1.1 correction describes MATO predictions by retrieval time and marks them “Da aggiornare” after two minutes; MATO source timestamps are unavailable, so retrieval time is not proof of live source freshness. An itinerary is not continuously monitored for disruption or a missed connection. No code currently ties a selected MATO leg to a GTT board and replans it.

Selecting Mezzi is the request action; there is no separate MATO consent toggle. Describe this accurately in user documentation. MATO's unresolved reuse/availability policy should remain visible as an experimental-service limitation.

## 0.1.6 scope and acceptance

Released 0.1.6 implements the following contract for one locally saved planning itinerary, saved stop shortcuts, bounded storage-failure diagnostics and reproducible native compiler path mapping. Source/browser review and the signed artifact passed; Android interaction acceptance remains open. Existing manual provider actions, local-only search policy, favourites format and foreground location model are preserved.

- **Save and restore the selected itinerary.** Explicit save retains the selected alternative, query, labels, geometry, steps/legs and original retrieval timestamp; the save timestamp is separate. Restore after reload/offline opens that snapshot and selected alternative without route, search, arrival or location requests. Reopened source data stays honestly aged. A pending request from the previous planner view cannot replace the restored snapshot.
- **Refresh and remove deliberately.** Explicit refresh may request current routing once. Failure retains the displayed snapshot and its source age; success retains the selected alternative when identity permits. Neither outcome changes saved bytes until another explicit save. Removing the saved itinerary removes its key and closes its restored view; a late read/request cannot resurrect it.
- **Save exact stop shortcuts.** Save uses the installed stop ID and retains its code, coordinates and dataset version. Opening requires an exact current ID/code/coordinate match; missing or changed records remain unavailable and removable. A valid shortcut opens that current board through its existing arrival/alert actions, without route, search or location requests. Save/remove operations remain ordered and bounded.
- **Keep committed data through failure.** Versioned journey and stop keys validate nested fields and size limits independently. Corrupt/unsupported/oversized reads stay unavailable; failed writes/removals retain the previously committed value. Races between hydration and explicit operations cannot publish obsolete values. Expected validation/limit/unavailable-stop states remain actionable in the UI.
- **Report only fixed local failure codes.** Read/write/remove failures and invalid persisted input may record the four allowlisted saved-travel codes. Names, coordinates, identifiers, saved payloads and raw errors never enter diagnostics. Expected limits, not-ready actions and stale/missing stop matches generate no diagnostic event. Existing recording preference, preview/manual copy/off/clear and byte/event bounds still apply.
- **Build and inspect the release.** The normal build appends environment-derived Clang path mappings while preserving signing, bundled JavaScript and native sources. Verify the expected certificate, public revision/version, permissions/backup, Google-free runtime graph, 16 KB ZIP/ELF alignment and all-entry private-content scan on the final artifact. A dirty-checkout validation artifact is not release evidence.

Native save/restore/contact/map/location/lifecycle, force-stop persistence, accessibility and physical same-key upgrades remain device checks. Stored routes remain planning snapshots; spoken guidance, active/background navigation and automatic provider monitoring require their own implementation and acceptance.

## Active-view transit refresh: in development

This scope targets foreground refresh and correct retrieval age. Source integration, manual acceptance, independent review and a new release remain pending. Journey-to-GTT stop-link UI is deferred to a separate small PR; it is not included in this scope.

- **Preserve retrieval age.** GTT cache hits retain the original `fetchedAt`; departure windows and prediction age are evaluated at the current time. Arrivals and alerts have independent retrieval timestamps, source timestamps, errors and retained snapshots. Failure never renews age or turns unavailable alerts into an empty successful result.
- **Refresh only the active view.** Target intervals are 60 seconds for arrivals, 300 seconds for alerts and 120 seconds for transit plans. Roads have no automatic refresh. Saved restoration makes no provider/location call and stays unarmed until explicit refresh of that query; automatic updates never write saved bytes.
- **Suspend synchronously.** Hidden views, Privacy, inactive/background AppState and unmount cancel timers and abort in-flight/queued work. Late completion cannot publish after suspension or an identity change. Resume permits at most one overdue request per resource, without catching up missed intervals.
- **Bound requests and retain data.** Manual/timer requests coalesce while pending; resource backoff is capped at 15 minutes and manual refresh respects the existing rate-limit cooldown. Same-query failure retains displayed data and its age; arrivals and alerts can succeed or fail independently. Cache hits cannot create a retry loop.
- **Keep the selected preview explicit.** If its stable ID disappears from fresh alternatives, retain its old geometry/time with a stale notice. Only explicit selection or reappearance of that ID changes the displayed itinerary. Saving that retained selection is disabled until a fresh alternative is chosen; an existing saved snapshot remains untouched.

Acceptance requires deterministic cadence/cache/identity/lifecycle tests, simulated browser request counters and the affected Italian/narrow-layout flows, plus `bun run verify` and independent review. Android foreground/background/screen-lock/return, real-provider cadence and battery behavior remain device checks; browser fixtures do not establish those outcomes.

## First Android device session: acceptance evidence

Run these after the installation steps in [android.md](android.md). Record app version, Android version, permission/network state and the exact query or public stop code for each failure. Private home/work coordinates are unnecessary for reports.

1. **Launch and browsing.** With Metro stopped and no Play services in the app's profile, launch, pan/zoom, select a map marker and open/close a sheet using Android back. Pass: real map and local results render, controls remain reachable, and no exit/crash occurs during these transitions.
2. **Discovery and local-only search.** Center within the packaged data bounds; try food/shop categories, plural aliases, a known public venue with a one-letter typo and a street address. Open a food place and a shop. Enable **Solo ricerca locale**, restart and confirm no Photon request during startup or searches; move outside coverage and inspect the outline, radius and capped/empty-result wording. Pass: relevant places retain sources/contact details, saved policy is honored, deliberate missing-data states remain visible and neither uncertain hours nor completeness is invented. A missing name is evidence to investigate, not proof that the business closed.
3. **Permission and origin.** Deny location, plan a walking journey using a chosen map point, then test approximate and precise permission outdoors. During a pending GPS request, choose a manual origin. Pass: the manual choice wins; GPS failure leaves browsing usable; the indicated origin matches the chosen point. The blue point is a captured location, not active tracking.
4. **Road planning.** Use a public destination a few kilometres away and compare walking, bicycle and car. Pass: modes produce plausible paths, distance/duration/steps agree with the map, and the interface never claims navigation has started. Check the arrival entrance and crossings on a familiar walking route.
5. **A real transit journey.** In the rebuilt transit release, plan between two public destinations within the supported network and choose a vehicle result plus a transfer result. Compare alternatives, departure/arrive-by selection, boarding stop, direction, alighting stop and arrival against the operator. Pass: the selected map path and leg details agree, supplied codes/platforms are shown, a cancelled/unknown leg stays explicit and a failed same-query refresh retains the old journey with its age. An all-walking result does not validate vehicles or transfers.
6. **At a stop.** Open the actual public stop code shown on the sign, including the correct side/direction. Compare the next reported departure with the operator. Refresh once, then disconnect for more than two minutes. Pass: no new “live” prediction is fabricated, existing data ages to stale, and unavailable alerts remain distinct from an empty alert list. Empty predictions are allowed; they must not mean “no service”.
7. **Persistence, upgrades and lifecycle.** Save a business, selected itinerary and stop shortcut, then force-stop/relaunch and change connectivity. Restore the itinerary without routing/search/arrivals/location requests; verify its original source age, explicit refresh and failed-write/removal behavior. Background during a position request. Install a later same-key release through the public download or Obtainium path without uninstalling. Pass: saved items/preferences persist after restart and upgrade, the expected version is installed, and interrupted requests recover through a useful action. Unpersisted itineraries still disappear; checking for updates without a newer build does not prove upgrade preservation.
8. **Comfort and accessibility.** Repeat search/place/route/stop flows with large system text and TalkBack if used. Pass: labels and primary actions remain readable and reachable. Record a 20–30 minute normal-use battery observation as a baseline, not a navigation battery benchmark.

The first session is complete when every step has an observed result, including “unavailable from provider” or a recorded known gap. A successful APK install alone does not close the native runtime gate.

## Data and provider constraints

- **Overture complements OSM; it does not provide Google's business corpus.** Broader downloads can improve coverage without phone accounts or a paid backend, but increase data-preparation/update work. Rich hours/reviews/traffic are separate source problems. See [place discovery](../research/place-discovery.md).
- **Photon is a name/address geocoder, not a complete restaurant-nearby API.** The current category chips deliberately stay local. Better citywide discovery should come from a prepared POI index or a separately evaluated permitted service, not repeated broad public-geocoder calls.
- **FOSSGIS remains modest-use, rate-limited, best-effort routing.** Automatic rerouting must respect its usage policy; a navigation loop cannot simply call it on every location update. See [online services](../research/online-services.md).
- **Provider queues recheck monotonic deadlines after early timer wakes.** Released 0.1.5 preserves start-to-start intervals and the 429 cooldown with deterministic early-wake and cancellation regressions. Timer punctuality and wall-clock corrections cannot shorten those queued deadlines; automatic refresh must still respect each provider's usage policy.
- **GTT static and realtime data must stay compatible.** The installed trip lookup can become obsolete even when the feed downloads successfully; refreshing the current package requires developer preparation and a new APK. A scheduled-departure fallback needs additional timetable data and service-calendar handling.
- **MATO's technical accessibility is not a service guarantee or settled reuse contract.** Resolve that dependency before treating transit planning as dependable. An alternative provider should be evaluated against coverage, terms and privacy; accounts or a hosted engine are not automatic prerequisites for the next UI iteration.
